# Consolidated Worker Service — Multi-Role Container with Shared Ramdisk

**Date:** 2026-03-17
**Status:** Draft
**Scope:** Enable comma-separated `ROLE` values in `run.sh`, consolidate ramdisk-eligible roles into a single `worker` service managed by supervisord

## Problem

Each ramdisk-eligible role (`scheduler`, `concurrency-scheduler`, `ws-server`) runs in its own container. Because tmpfs is per-container (cannot be shared across mount namespaces), each container creates its own ramdisk copy of `/var/www` (~130MB). On a 4GB Raspberry Pi, 3x 130MB = ~390MB of RAM for three identical copies of the same read-only data.

## Solution

Allow `ROLE` to accept a comma-separated list (e.g., `ROLE=scheduler,concurrency-scheduler,ws-server`). When multiple roles are specified, all processes run under supervisord within a single container, sharing one ramdisk. Single-role deployments remain unchanged.

## Design

### Multi-Role Parsing

`run.sh` parses `ROLE` into a bash array:

```bash
IFS=',' read -ra ROLES <<< "${ROLE:-}"
```

A helper function checks if a role is in the array:

```bash
has_role() {
    local target="$1"
    for r in "${ROLES[@]}"; do
        if [[ "$r" == "$target" ]]; then
            return 0
        fi
    done
    return 1
}
```

- `ROLE=scheduler` → `ROLES=(scheduler)` — single-role, existing behavior
- `ROLE=scheduler,concurrency-scheduler,ws-server` → `ROLES=(scheduler concurrency-scheduler ws-server)` — multi-role, supervisord mode

### Single-Role vs Multi-Role Branching

The existing `if/elif` chain in `run.sh` stays intact for single-role deployments (when `ROLES` has exactly one element). Multi-role mode is a new branch that activates when `${#ROLES[@]} > 1`:

```
if [[ ${#ROLES[@]} -gt 1 ]]; then
    # Multi-role: shared init + supervisord
else
    # Single-role: existing if/elif chain, unchanged
fi
```

This ensures zero behavioral change for existing single-role deployments.

### Shared Initialization (Multi-Role Only)

When multiple roles are specified, a shared housekeeping phase runs **once** before supervisord starts:

```bash
php artisan cache:clear
php artisan queue:flush
php artisan queue:restart
```

These commands currently run inside the `concurrency-scheduler` role block. In multi-role mode, they run once regardless of which roles are active, since all roles benefit from a clean cache/queue state.

### Supervisord Program Generation

A new script `internal/generate-supervisor-configs.sh` creates `.conf` files in `/tmp/supervisor/` based on which roles are in the `ROLES` array. It accepts the roles as arguments.

#### scheduler role generates:

**`/tmp/supervisor/cron.conf`:**
```ini
[program:cron]
command=cron -f
autorestart=true
stdout_logfile=/tmp/supervisor/logs/cron.log
stderr_logfile=/tmp/supervisor/logs/cron.log
```

**`/tmp/supervisor/short-schedule.conf`:**
```ini
[program:short-schedule]
command=php artisan short-schedule:run
autorestart=true
startsecs=0
stdout_logfile=/tmp/supervisor/logs/short-schedule.log
stderr_logfile=/tmp/supervisor/logs/short-schedule.log
```

Note: `crontab /var/www/internal/cron/crontab` must be called before supervisord starts (in the shared init phase when scheduler is in the role list).

Note: `short-schedule:run` runs once and exits. With `autorestart=true` and `startsecs=0`, supervisord treats immediate exits as normal and restarts the process, replicating the existing `while true` loop behavior. Without `startsecs=0`, supervisord would consider an immediate exit as a crash and eventually enter `FATAL` state.

#### concurrency-scheduler role generates:

**`/tmp/supervisor/concurrent-run.conf`:**

Note: Queue worker `.conf` files (e.g., `prints.conf`, `recordings.conf`) are **not** generated by this script. They are dynamically managed at runtime by the `RefreshPrinterWorkers` PHP concurrent service (`app/Console/Services/Concurrent/RefreshPrinterWorkers.php`), which writes configs to `/tmp/supervisor/` and calls `supervisorctl reread && supervisorctl update`. This existing mechanism works unchanged — it just needs supervisord to be running, which both single-role and multi-role modes ensure.

**`/tmp/supervisor/concurrent-run.conf`:**
```ini
[program:concurrent-run]
command=php artisan concurrent:run-indefinitely
autorestart=true
stdout_logfile=/tmp/supervisor/logs/concurrent-run.log
stderr_logfile=/tmp/supervisor/logs/concurrent-run.log
```

**`/tmp/supervisor/log-rotator.conf`:**
```ini
[program:log-rotator]
command=bash -c 'while true; do for log in /tmp/supervisor/logs/*.log; do truncate --size 512K "$log"; done; sleep 60; done'
autorestart=true
stdout_logfile=/dev/null
stderr_logfile=/dev/null
```

#### ws-server role generates:

**`/tmp/supervisor/reverb.conf`:**
```ini
[program:reverb]
command=php artisan reverb:start --host 0.0.0.0 --port 6001
autorestart=true
stdout_logfile=/tmp/supervisor/logs/reverb.log
stderr_logfile=/tmp/supervisor/logs/reverb.log
```

### Startup Flow (Multi-Role)

```
1. Existing shared init (PATH, storage dirs, OPcache, hardware detection, ramdisk setup)
2. Parse ROLE into ROLES array
3. Multi-role branch:
   a. Shared housekeeping (cache:clear, queue:flush, queue:restart)
   b. Install crontab if scheduler is in ROLES
   c. Run generate-supervisor-configs.sh with ROLES as arguments
   d. mkdir -p /tmp/supervisor/logs
   e. Start supervisord in foreground (nodaemon=true)
```

Supervisord with `nodaemon=true` runs in the foreground, keeping the container alive. All process restart logic is handled by supervisord's `autorestart=true`.

### Supervisord Configuration Change

The existing `internal/supervisor/supervisord.conf` needs `nodaemon=true` added to the `[supervisord]` section so it runs in the foreground for multi-role mode:

```ini
[supervisord]
nodaemon=true
logfile=/tmp/supervisord.log
pidfile=/tmp/supervisord.pid
```

**Impact on single-role `concurrency-scheduler`:** The existing code calls `supervisord` as a background daemon, then runs `concurrent:run-indefinitely &` and a blocking `while true` log rotation loop. With `nodaemon=true`, supervisord would block and never reach those lines. The fix: update the single-role `concurrency-scheduler` path to also use `generate-supervisor-configs.sh` and run supervisord in the foreground. This means the single-role concurrency-scheduler path generates its supervisor configs (concurrent-run, log-rotator, queue workers), then starts supervisord with `nodaemon=true` — effectively the same as multi-role mode with one role. This is a simplification that removes the manual backgrounding/loop logic while preserving identical behavior.

### Ramdisk Integration

`ramdisk-setup.sh`'s `check_role_eligible()` currently matches `$ROLE` as a single string. It needs to parse comma-separated values:

```bash
check_role_eligible() {
    local role_str="${ROLE:-}"

    if [[ -z "$role_str" ]]; then
        log_info "No ROLE set, skipping ramdisk"
        return 1
    fi

    IFS=',' read -ra roles <<< "$role_str"

    for role in "${roles[@]}"; do
        for eligible in "${ELIGIBLE_ROLES[@]}"; do
            if [[ "$role" == "$eligible" ]]; then
                return 0
            fi
        done
    done

    log_info "No eligible role found in '$role_str', ramdisk not needed"
    return 1
}
```

### Docker Compose Changes

Replace three services with one `worker` service:

```yaml
worker:
  image: docker.io/wprint3d/wprint3d:latest
  restart: always
  logging:
    driver: ${CONTAINER_LOG_DRIVER:-local}
    options:
      max-size: "1m"
      mode: non-blocking
  privileged: true
  environment:
    - ROLE=scheduler,concurrency-scheduler,ws-server
    - COMPOSE_DIR=${PWD}
    - QUEUES=default:1,recordings:1,broadcasts:2,prints,previews,snapshots
    - SLEEP=5
  volumes:
    - /dev/bus/usb:/dev/bus/usb
    - /dev:/dev
    - /var/run/docker.sock:/var/run/docker.sock
    - /proc:/proc
    - storage:/var/www/storage
    - proxy:/var/www/proxy/internal
    - startup:/var/www/internal/startup
    - ./wprint3d-config:/var/www/.external-configs
    - ${PWD}:${PWD}
  depends_on:
    - redis
    - mongo
```

**Volume union:** The worker service mounts the union of volumes from all three replaced services. The `ws-server` currently mounts `/var/run/docker.sock` and `/proc` — these are included. The `scheduler` and `concurrency-scheduler` don't mount them but having them available causes no harm.

**Removed services:** `scheduler`, `concurrency-scheduler`, and `ws-server` are removed from docker-compose.yml.

**Proxy dependency:** The `proxy` service currently `depends_on: ws-server`. This changes to `depends_on: worker`.

### Backward Compatibility

- **Single-role deployments** work exactly as before. The `if/elif` chain is untouched.
- **Users who prefer isolation** can keep separate services by defining them with single `ROLE` values in their own docker-compose override file.
- **No new environment variables** are introduced. The existing `ROLE` variable gains comma-separated support.

## Testing Strategy

- Verify single-role `ROLE=scheduler` still works identically (no supervisord, existing behavior)
- Verify single-role `ROLE=concurrency-scheduler` still works identically
- Verify single-role `ROLE=ws-server` still works identically
- Verify multi-role `ROLE=scheduler,concurrency-scheduler,ws-server` starts all processes under supervisord
- Verify shared init runs once (cache:clear, queue:flush, queue:restart)
- Verify cron and short-schedule both run simultaneously in multi-role mode
- Verify Reverb starts on port 6001 in multi-role mode
- Verify queue workers start with correct QUEUES configuration in multi-role mode
- Verify ramdisk is created once for the combined worker container
- Verify `supervisorctl status` shows all expected programs running
- Verify process restart: kill a managed process, confirm supervisord restarts it
- Verify log rotation works for supervisor logs
- Verify proxy service correctly depends on worker instead of ws-server
